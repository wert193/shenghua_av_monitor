# ④ 踩坑清单：触发条件、定位步骤与处置

**适用场景**：PYNQ / Zynq 上做自定义 Overlay 的音视频工程，出现"仿真全过但上板不对""数值对不上""播放不连续""测量不可信"时。
**使用方法**：先用**触发条件**判断你是否真的踩了这条坑，再按**排查步骤**逐步收敛（每步都应能在一分钟内给出是/否），最后按**处置**落地，并用**验证**确认修好。
**已验证效果**：下列 26 条全部来自本工程真实发生的问题；标 ✅ 的条目在板端复测通过。
**失效条件**：与 Xilinx 工具版本相关的条目（已标注 2024.1）换版本后需重新确认；纯软件项目用不到 PL 类条目。

---

## A. 复位、加载与配置

### A1. 仿真通过、综合通过，上板完全不动 ✅

- **触发条件**：位流能下载、Overlay 能加载、软件读寄存器也不报错，但硬件功能没有任何反应。
- **根因（本工程实例）**：`aux_reset_in` 端口是**低有效**，却接了常量 0，fabric 一直保持在复位。
- **排查步骤**：① 确认 `ap_idle`/`ap_done` 或自定义状态位是否恒为复位值；② 打开 IP 的复位配置（`C_EXT_RESET_HIGH` / `C_AUX_RESET_HIGH`）核对极性；③ 在 RTL 里对复位信号加一个可见的计数器输出，直接观察；④ 用逻辑分析（ILA）确认时钟与复位是否真的到达模块。
- **处置**：`C_EXT_RESET_HIGH=0` + `C_AUX_RESET_HIGH=1`（或将输入接高），重新综合布线生成配套 bit/HWH；在加载前用脚本检查 HWH 的复位配置并拒绝旧版本。
- **验证**：重建后时序通过（本工程 WNS +1.176 / WHS +0.012 ns），四模式上板 PASS。

### A2. bit 与 HWH 不配套，软件"看起来正常"但行为错 ✅

- **触发条件**：手工从多个 build 目录里挑文件打包；或迭代多轮后目录里有多个 `audio_live.bit`。
- **现象**：Overlay 加载成功、地址能读到，但写进去的数据不生效或行为与预期不符。
- **根因**：HWH 决定 IP 名称、地址映射与中断号；与 bit 不配套就会映射到错误地址。
- **排查步骤**：① `diff` 两个 HWH 的地址段；② 检查打包脚本是否从同一目录取 bit 与 HWH；③ 对比 HWH 时间戳与 build 标记。
- **处置**：一个交付包只认**一对**配套 bit/HWH；打包脚本在打包前校验 `BUILD_OK`、时序通过字样与 HWH 关键地址。
- **验证**：打包器拒绝加载不配套的 HWH（本工程用已知错误 HWH 做过反向验证）。

### A3. `overlay.ip_dict` 找不到外设，直接判定"配置不含该功能" ✅

- **触发条件**：访问 HWH 中 `MEMTYPE=MEMORY` 的 BRAM（如 HDMI 帧缓冲）。
- **现象**：接口返回 400 或"此配置未包含 X"，但硬件其实在。
- **根因**：这类 BRAM 出现在 `overlay.mem_dict` 而不是 `overlay.ip_dict`。
- **排查步骤**：① 打印 `overlay.ip_dict.keys()` 与 `overlay.mem_dict.keys()`；② 在 HWH 里搜该 IP 的 `MEMRANGE`；③ 确认地址空间是否与预期一致。
- **处置**：识别逻辑同时查两本字典；用 `pynq.MMIO(base, size)` 直接映射已核对的地址。
- **验证**：本工程修正后 `/api/hdmi/refresh` 由 400 变为 200，并在本地用 `mem_dict` 分支复现过该失败路径。

### A4. 一个 Overlay 还没卸载就加载另一个 ✅

- **触发条件**：连续 `%run` 两个启动器，或上一个 notebook 的 kernel 还在跑。
- **现象**：行为随机、DMA 报错、必须重启板卡。
- **排查步骤**：① 检查是否有其它 kernel 占用 UIO/Overlay；② 看日志里是否出现两次配置下载；③ 确认上一进程是否已退出。
- **处置**：换 Overlay 前先停应用、等 kernel 空闲；错误恢复要有超时与 DMA 复位；不要并行加载两个 Overlay。
- **验证**：本工程的启动器在 `finally` 中恢复 base overlay 与原服务，恢复失败会报告并要求重启板卡。

## B. DMA 与并发

### B1. 多个用户共用一条 DMA，读到别人的控制状态 ✅

- **触发条件**：音频块与视频帧共用一条 AXI DMA（本工程即如此）。
- **现象**：偶发数据错位、长度不对、DMA 报错。
- **排查步骤**：① 在日志里打时间戳，看两个任务的配置写入是否交错；② 检查"配置寄存器 → 启动传输 → 等完成"这段是否被整体保护；③ 用单任务模式复跑，判断是否只在并发时出现。
- **处置**：驱动层用**同一把锁**覆盖"配置 + 传输 + 状态清理"整个区间；任务完成后把路由控制字清零，避免下一个任务继承状态。
- **验证**：两轮 30 秒同源播放、1,440,127 采样、欠载 0（板端断言）。

### B2. `while not done` 没有截止时间，卡死无法诊断 ✅

- **触发条件**：任何 MMIO 轮询循环。
- **现象**：整块卡住，且**注意：被阻塞的单次 MMIO 访问无法被轮询截止时间打断**，超时定时器也可能不生效。
- **排查步骤**：① 给每个阶段打印进度（复位、启动通道、申请内存、编程长度、轮询）；② 每个轮询打印 MM2S/S2MM 状态寄存器；③ 用 15 秒 traceback 级别的 watchdog 日志判断卡在哪一步。
- **处置**：有界轮询（本工程 0.5–2 s）+ 分阶段日志 + 失败即复位 DMA 通道；不要复用已标记失败的驱动实例。
- **验证**：主机侧模拟 DMA 错误/超时/操作顺序检查通过。

### B3. 用 PYNQ 高层 DMA 构造导致启动无限等待 ✅

- **触发条件**：通道启动异常或器件未就绪时。
- **处置**：绕过高层构造，直接绑定 `overlay.ip_dict['axi_dma_0']` 的物理地址用 `MMIO` 编程寄存器（本工程做法），把超时控制权拿回自己手里。

## C. 数值一致性

### C1. 自然图上"看不出错"，边界差异被掩盖 ✅

- **触发条件**：ARM 与 FPGA 的边界策略或舍入规则不一致（例如一边 `BORDER_REPLICATE`、一边默认零填充）。
- **排查步骤**：① 先用**脉冲图**（角点与中心为 255）看输出边界；② 用 1×1、1×N、N×1 窄图放大边界效应；③ 用全黑/全白与饱和值检查截断；④ 逐像素 `max_error`，不要只看均值。
- **处置**：先冻结契约（格式、舍入、饱和位置、边界策略、最大尺寸），把 ARM 参考实现当作唯一数值标准，两边都按它写。
- **验证**：24 组向量 PASS 24/24；实板四种效果各 12 帧最大误差 0。

### C2. 板端 OpenCV 对退化尺寸报错 ✅

- **触发条件**：板端 OpenCV 4.5.4 上对 1×1 图调用 `filter2D`。
- **处置**：在参考实现里显式短路 1×1（边缘返回全零，其余返回自身拷贝），统一 `BORDER_REPLICATE`；把 1×1 用例写进仿真向量。
- **验证**：1×1 用例进入仿真并 PASS，实板该用例最大误差 0。

### C3. 大图分块出现接缝 ✅

- **触发条件**：工作图大于硬件核尺寸上限（本工程 320×240），按上限直接切块。
- **根因**：块边缘缺少真实邻域像素（3×3 核需要 1 像素 halo）。
- **处置**：块核心尺寸 = 上限 − 2×halo（本工程 318×238），块边界用**真实邻域**，只有真正的图像边界用复制填充；滤波后裁掉 halo 再拼接。
- **验证**：断言"所有 halo 接缝与边界精确"通过，实板 640×360 三效果最大误差 0。

### C4. 换了参考实现却沿用旧结论 ✅

- **触发条件**：修改了 ARM 参考实现、随机种子或测试图尺寸。
- **处置**：旧结论作废并重测；报告里记录实现标签（如 `shared-opencv-v1`）、输入 `sha256` 与系数 `sha256`；**不同尺寸的倍数不能直接相比**。

## D. 时序、资源与时钟域

### D1. 综合通过就以为时序没问题 ✅

- **触发条件**：只看了 HLS 的时序估算或综合报告。
- **处置**：一律看**布线后**报告（WNS/WHS/TNS/THS），并要求报告里出现 `All user specified timing constraints are met.`；HLS 估算与板级 WNS 可能差一个量级。

### D2. BRAM 接近满载时小改动导致布线失败 ✅

- **触发条件**：已用 130+/140 BRAM（本工程 138/140 = 98.57%）还想加帧缓存。
- **处置**：先看 utilization；优先把缓存搬到大容量外部存储或改成流式行缓存；用"逻辑换存储"（本工程新增两种效果只增加 545 LUT、BRAM 不变）。

### D3. 对整段路径做粗放时序例外 ✅

- **触发条件**：出现 CDC 违例，直接对整段路径 `set_false_path`。
- **处置**：只对**明确的双级同步器第一阶段**设例外，第二阶段保持约束；必要时在 RTL 里把同步器标注清楚。
- **验证**：本工程 HDMI 路径 WNS +0.292 / WHS +0.028 ns，TNS/THS 0。

### D4. 厂商 IP 自带 generated-clock XDC 与工程时钟冲突 ✅

- **触发条件**：使用 rgb2dvi 之类 IP，同时用工程内 clock wizard 产生像素时钟。
- **处置**：停用 IP 自带的 generated-clock XDC，保留其余时序/IO 约束。

### D5. BRAM 原生端口寻址模式用错 ✅

- **触发条件**：AXI BRAM controller 与原生 BRAM 端口混用。
- **现象**：软件写进去、硬件读出来地址错位。
- **处置**：controller 模式下原生端口使用**字节地址**；显示地址路径加流水。

### D6. 工具链把源路径写成错误的相对路径（2024.1 / Windows）

- **触发条件**：HLS 工程关闭后重新打开。
- **现象**：找不到源文件；元数据里 `tb="false"`。
- **处置**：关闭工程后直接改写 `hls.app`，把源文件路径替换为绝对路径，并把 `false` 映射为 `0`，再重新打开。

## E. 音频与播放

### E1. 用"提交了多少采样"推断播放正常 ✅

- **触发条件**：UI 上只有"已提交/已发送样本数"，没有硬件播放计数。
- **现象**：把"发出去"当成"播出来"。
- **处置**：加硬件播放计数与欠载计数（本工程 8192 样本 FIFO + 寄存器签名 `0x53414631`），用**已播样本数与秒数对账**；欠载要记录并终止会话，而不是悄悄拉长。
- **验证**：`submitted=1440127 played=1440127 seconds=30.004121 expected=30.002646 underruns=0`；反向案例（提交 1,352,647 / 已播 1,344,576、`stopped=1`）被正确判为失败。

### E2. 用时长粗算采样率 ✅

- **触发条件**：只测"播了多久 / 多少采样"。
- **现象**：480000 采样 / 9.837 秒被当成"精确 48 kHz"（与 10.000 秒差约 1.6%）。
- **处置**：不要用该口径下结论；用硬件计数对账，并明确"音频实际采样时钟未独立测量"。

### E3. 模式切换爆音、过渡中再切换跳变 ✅

- **处置**：960 样本（约 20 ms）线性交叉淡化；**过渡中再次切换要从当前混合值出发**，而不是从旧系数重新起步；开始、自然结束、请求停止都要走幅度斜坡；按键加 30 ms 稳定态去抖。
- **验证**：与独立 float64 全卷积 + 淡化参考比对，最大偏差约 2.86e-06。

### E4. 音响无声：插错接口 ✅

- **触发条件**：PYNQ-Z2 的音频输出口分 HP MIC 与 LINE IN。
- **处置**：接 **HP MIC**；LINE IN 不会出声。先排除物理层再排查软件。

## F. 测量口径与结论

### F1. 把对"加速方案"不利的成本删掉 ✅

- **触发条件**：FPGA 结果比 ARM 差，产生"只算纯计算时间"的念头。
- **处置**：保留边界填充、打包、DMA、回拷与锁等待；如实标注比值 <1 的含义，然后去**真正优化这些开销**（本工程 26.966 → 11.582 ms）。
- **验证**：优化后平滑仍为 0.66×，边缘 2.79×、锐化 1.33×，两个方向的数据都保留在报告里。

### F2. 用单算子倍数替代整链路结论 ✅

- **处置**：分两类口径分别报告——单次调用 vs 完整播放（含解码、合成、显示）；只有相同范围的数据才能算比值；CPU 占用要说明是整板 `/proc/stat` 归一化值。

### F3. 一次跑分当结论 ✅

- **处置**：固定预热（本工程 3 次）、多次测量（10–30 次）、报告均值与 P95；整段播放做多轮并保留逐帧/CPU 原始数据；输入用哈希核对；说明"不同机器不应以毫秒完全相等作为通过条件"。

### F4. 拿旧构建的数值描述新功能 ✅

- **处置**：保留构建版本号与产物 SHA-256；换 build 后旧数值不得复用，报告里注明该数值属于哪个构建。

## G. 发布与协作

### G1. 提交前没看 Git 跟踪列表

- **触发条件**：`git add -A` 之前没有逐项确认。
- **处置**：排除用户媒体、生成启动器（内嵌媒体）、Vivado 临时工程与缓存、测试截图、本机绝对路径与主机名、板卡固定 IP；保留最终 build、第三方来源、实测摘要与失败边界。用 [`checks/verify_repo.py`](checks/verify_repo.py) 自动检查。

### G2. 用"内嵌媒体的单文件启动器"充当源代码

- **处置**：提交源码 + 可复现脚本；媒体由使用者自备并确认授权；生成的启动器列入 `.gitignore`。

### G3. 把未验证的内容写成已验证

- **处置**：每个 README/报告都保留"边界与未验证项"章节，逐版更新状态；本工程两处历史故障（整板网络不可达、HDMI 无信号）根因至今未定位，如实标注。
