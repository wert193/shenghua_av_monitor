# 工程骨架模板（ARM/FPGA 协同题目）

**适用场景**：新开一个 ARM/FPGA（PS+PL）协同题目、或把一个"能跑的单算子 demo"整理成可交付/可开源工程时。板卡与算法无关，适用于任何"PL 出算子、PS 管系统"的项目。
**使用方法**：按本文目录建好 6 个顶层目录，把现有散落文件按"谁消费它"归位；再用文末 6 步改造清单逐条消除"产物进版本库""数据不可入库""报告与代码脱节"三类问题。
**已验证效果**：本仓库的 `build/ board/ data/ fpga/src/ report/ skill/` 结构即按此骨架落地，并有实文件可查：向量与黄金值见 [`fpga/src/sim/data/vectors/vectors.hex`](../../fpga/src/sim/data/vectors/vectors.hex) 与 [`metrics/logs/rtl_simulation.txt`](../../metrics/logs/rtl_simulation.txt)，脱敏实测见 [`metrics/logs/video_effects_board_check.summary.json`](../../metrics/logs/video_effects_board_check.summary.json)，构建证据见 [`fpga/report/timing.rpt`](../../fpga/report/timing.rpt) 与 [`fpga/report/ppa_evolution.csv`](../../fpga/report/ppa_evolution.csv)。
**失效条件**：纯软件项目、不下板的算法研究、不需要 ARM/PL 数值对账的项目不需要该骨架（多出的目录只会增加维护面）；若团队已有强制提交结构，则只借用本骨架的"最小文件清单"与三条原则，目录名按提交要求改名，并在 README 里给出目录对照表。
**关于本文引用的路径**：`skill/templates/` 目录本身在撰写时已建立（即本文件所在目录）；仓库中部分索引（如 `skill/README.md` 提到的 `skill/checks/`）指向尚未提交的文件，落地时应先确认目标文件存在再建链接。

## 1. 六个顶层目录

### `build/` —— 构建入口与构建证据

| 项 | 内容 |
|---|---|
| 放什么 | 一键构建脚本（跨平台各一份）、产物归档目录 `final/`、工具生成的报告 `reports/`（时序、资源、DRC、HLS 综合/联仿）、里程碑阶段的同格式报告快照、PPA 演进表 |
| 谁消费它 | 评审/复现者（只看这里就能判断构建是否成功）；下一阶段优化时的对比基线 |
| 最小文件清单 | 构建入口脚本 ×1（Windows 或 Linux 均可）、`README.md`、`final/BUILD_OK` 之类可机读的成功标记、`timing.rpt`、`utilization.rpt`、`drc.rpt`、`ppa_evolution.csv` |
| 存在的理由 | 把"构建是否通过"变成**文件是否存在、报告是否含通过字样**，而不是"我本机跑过"。没有它，性能与资源结论无法被复核 |

### `board/` —— 上板脚本与板端实测

| 项 | 内容 |
|---|---|
| 放什么 | 素材准备脚本、打包/启动脚本、板端校验驱动、脱敏汇总器、`measurements/` 下的可提交实测摘要 |
| 谁消费它 | 复现者（按步骤操作板卡）；报告章节的数字全部从 `measurements/` 取 |
| 最小文件清单 | `README.md`（含操作顺序、退出方式、故障定位顺序）、板端校验脚本 ×1、脱敏汇总脚本 ×1、至少一份脱敏实测 JSON |
| 存在的理由 | 板端原始报告通常含本机路径、进程号、媒体名，**不能直接入库**；这一层是"原始 → 可提交"的必经转换，也是把实测与报告连起来的唯一入口 |

### `data/` —— 测试数据与黄金参考

| 项 | 内容 |
|---|---|
| 放什么 | 向量生成器的输出（输入 + 黄金期望输出）、系数/量化中间结果、仿真结论文本、实测 CSV、产物哈希清单 |
| 谁消费它 | 仿真（读向量）、板端校验（读黄金值判定最大误差）、评审（核对"结论有数据支撑"） |
| 最小文件清单 | 至少一组"输入 + 黄金期望输出"文本向量、一份仿真结论、一份实测汇总表、`README.md` |
| 存在的理由 | 让"数值正确"可脱离原作者的机器独立重跑；黄金参考入库后，未装 OpenCV/未装工具链的机器也能复跑仿真 |

### `fpga/src/` —— 所有可编译源码

| 项 | 内容 |
|---|---|
| 放什么 | `rtl/`（含 testbench）、HLS 核与 C 仿真、ARM 参考核与驱动、板端 Python 应用、构建 Tcl、系数生成脚本、`vendor/`（第三方 IP 及来源哈希） |
| 谁消费它 | 构建脚本、仿真流程、板端启动器打包脚本 |
| 最小文件清单 | RTL 顶层 + testbench、HLS 顶层函数 + 测试、ARM 参考实现、一份"PL 与 PS 数值契约一致"的说明或测试、构建 Tcl |
| 存在的理由 | 把"源码"与"构建产物"分开：源码进版本库，`fpga/src/build/` 下的 Vivado 工程与综合产物不进 |

### `report/` —— 报告与协作记录

| 项 | 内容 |
|---|---|
| 放什么 | 设计与实现报告、大模型协作记录、工程决策记录、图表（`figures/`） |
| 谁消费它 | 评审；下一届/下一个队伍 |
| 最小文件清单 | 设计报告 ×1、协作记录 ×1、`figures/` 至少一张真实截图 |
| 存在的理由 | 报告与代码同级，才能保证"改代码就改报告"；报告放在别处时，数字与代码版本很容易分叉 |

### `skill/` —— 可复用经验

| 项 | 内容 |
|---|---|
| 放什么 | 提示词工作流、`templates/`（本文件所在类别）、`checks/`（可执行校验脚本）、踩坑清单、与本队题目解耦的通用技能 |
| 谁消费它 | 下一个做同类题目的队伍 |
| 最小文件清单 | `README.md`（索引，每条含适用场景/使用方法/已验证效果/失效条件）、至少一个可重跑的校验脚本或模板 |
| 存在的理由 | 交付物里最容易缺、也最容易被评委追问"经验能否复用"的一项；只收录**真实发生过**的问题，每条配一个可重跑的检查 |

## 3. 三条原则（违反其中任何一条，交付都会返工）

1. **源码与产物分离，生成物不进版本库。** `fpga/src/build/`、Vivado 工程、综合/实现中间目录、`dist/` 启动器、媒体素材一律排除；只提交**能重建它们的脚本**与**最终报告**（bit/HWH 是否提交按评审要求决定，并在 README 里写明）。
2. **数据/黄金参考必须可入库且不含隐私。** 向量、系数、CSV、摘要 JSON 要小、文本化、可 diff；不得含本机绝对路径、用户名、主机名、板卡 IP、进程号、媒体文件名与标题。原始板端报告先过脱敏汇总器再入库。
3. **报告与代码同级、可追溯。** 报告里的每个数字都要能指到 `metrics/logs/` 或 `metrics/logs/` 的具体文件与字段；每个性能指标都带**计时口径字符串**；改代码必须回头改报告，不允许"报告说 A、代码做 B"。

## 4. 从单算子 demo 升级为可交付工程：6 步改造清单

1. **冻结数值契约**（先做，否则后面全是返工）：写下输入格式、边界策略、舍入与饱和位置、误差判定标准（本项目定为"最大误差 = 0"），并让 ARM 侧与 PL 侧共用同一份描述。
2. **抽出 ARM 参考实现并统一调用点**：把散落在测量脚本里的多套实现合并为一个函数，加实现标签（如 `shared-opencv-v1`），旧实现的耗时不再用于新结论。
3. **生成并提交向量**：用固定随机种子产出"输入 + 黄金期望输出"，覆盖退化与极端用例，文件写进 `fpga/src/sim/data/vectors/`，并在 `data/README.md` 说明生成命令。
4. **建 `build/` 并固化报告归档**：一键脚本跑完后自动收集时序/资源/DRC，检查通过字样与 `BUILD_OK`，把阶段报告快照进 `reports/milestones/`，同步更新 `ppa_evolution.csv`。
5. **建 `board/`：校验驱动 + 脱敏汇总**：先用校验脚本对每个效果/模式断言关键计数（误差 0、欠载 0、样本数一致），再用脱敏器把原始 JSON 转成可提交摘要，最后把摘要与报告表格对齐。
6. **补 `skill/` 与"边界与未验证项"**：只收录真实踩过的坑，每条配可重跑检查并写明失效条件；在报告与 README 中逐条列出未验证项（物理链路、端到端时延、未覆盖工况），不用"应该可以"替代证据。
