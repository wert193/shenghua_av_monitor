# 设计/实现报告模板（章节骨架 + 表格）

**适用场景**：给一个下板的 ARM/FPGA 协同作品写设计与实现报告，或把已有的技术总结改写成"评审能逐条核对"的报告时。
**使用方法**：按下面 10 个章节顺序填空。每章分三小节——**要回答的问题 / 必填字段 / 常见漏项**；先把必填字段凑齐（缺哪个字段就去补测量或补实验），再写叙述文字；两个表格模板直接复制，逐行替换成自己的数据。
**已验证效果**：本仓库 [`report/design_report.md`](../../report/design_report.md) 即由该骨架展开（十章齐备：选题背景与创新点、设计原理与功能框图、软硬件划分依据与接口设计、优化过程与对比表、大模型协作、技能包提炼、复现说明、边界与未验证项、结论与后续工作），其中每个数字都能指回 `metrics/logs/` 或 `metrics/logs/` 的具体文件（如 [`metrics/logs/full_playback_rounds.json`](../../metrics/logs/full_playback_rounds.json)、[`fpga/report/ppa_evolution.csv`](../../fpga/report/ppa_evolution.csv)）。
**失效条件**：若评审明确不要求口径声明与未验证项，可以精简叙述，但**不要删除**"验证方法与数值契约""边界与未验证项"两章——删掉之后报告里的性能数字就无法被复核，反而更容易被质疑。纯软件项目可删去软硬件划分、资源与时序两节；没有用大模型的可删协作记录章，但不得虚构。

## 0. 摘要（可选但强烈建议）

- **要回答的问题**：评审只看这一页，能不能知道作品做了什么、结果如何、边界在哪？
- **必填字段**：作品名、**目标器件全型号**、**工具与版本**、PL 时钟频率、功能一句话、资源与时序一行、数值正确性一行、性能两行（单算子口径 / 整链路口径）、**明确不宣称什么**一行。
- **常见漏项**：只写"加速比 N×"不写口径；器件只写板卡名不写型号；工具版本缺失（`Vivado 2024.1` 而不是"最新版 Vivado"）。

### 章节速览（先凑字段，再写叙述）

| # | 章节 | 这一章必须回答的一句话 | 最容易缺的字段 |
|---|---|---|---|
| 1 | 选题背景与创新点 | 前人做到哪、我的差别是什么且有何证据 | 创新点的证据文件路径 |
| 2 | 设计原理与功能框图 | 数据怎么流、时钟域怎么分、数值契约是什么 | 数值契约（舍入/饱和位置） |
| 3 | 软硬件划分依据与接口 | 每个功能为什么放 PS 或 PL、共享资源怎么互斥 | 加锁策略与轮询超时 |
| 4 | 验证方法与数值契约 | 凭什么说正确、容差多少、哪些没测 | **计时口径字符串**、未覆盖工况清单 |
| 5 | 优化过程与对比表 | 每轮改动的资源/时序/性能变化与瓶颈 | 优化前数据、对己方不利的数字 |
| 6 | 大模型协作记录 | 哪些模型判断被实测推翻、怎么发现 | 被推翻判断的证据 |
| 7 | 技能包提炼过程 | 经验从哪来、怎么证明有效、失效条件 | 每条经验对应的可重跑检查 |
| 8 | 复现说明 | 陌生人能否从零复现出同类结论 | 每步的通过判据 |
| 9 | 边界与未验证项 | 哪些结论没被验证、何时不成立 | 未验证项清单 |
| 10 | 结论与后续工作 | 实际达到什么、下一步按什么优先级 | 后续工作的约束依据 |

### 通用必填字段怎么填

| 字段 | 填法要求 | 反例 |
|---|---|---|
| 目标器件与工具版本 | 写全型号与精确版本：`XC7Z020CLG400-1`；`Vivado 2024.1 / Vitis HLS 2024.1 / 板端镜像版本` | "Zynq 开发板""最新版 Vivado" |
| 时钟频率 | 写 PL 主时钟、像素/音频时钟及其域关系 | "100 MHz 左右" |
| 资源占用 | 布线后 LUT / FF / BRAM / DSP 的绝对数与器件占比 | 只给百分比不给绝对数 |
| WNS / WHS / TNS / THS | 布线后四个值全给，并注明来自哪份报告 | 只写"时序通过" |
| 每条性能指标的计时口径字符串 | 一句话写清"从哪到哪、含什么、不含什么"，随数据落盘 | "耗时 11.5 ms" |
| 逐像素 / 逐样本误差 | 给**最大值**而不是平均值，并写明判定标准 | "误差很小""基本一致" |
| 未验证项清单 | 逐条编号，写清"为什么没验证"与"怎么才算验证" | 用"应该可以"带过 |

## 1. 选题背景与创新点

- **要回答的问题**：这个问题为什么值得做？前人做到哪一步？你的差别是什么（且差别有证据）？
- **必填字段**：4 类真实痛点（每条对应一个工程约束）、基线对照对象（官方 overlay/公开同类作品，附链接）、创新点表（每条含"与常见做法的差别" + **证据文件路径**）、明确的范围（做/不做）。
- **常见漏项**：创新点写成形容词（"性能优异"）而无证据；不引用前人工作；不写"不做"的部分，导致后面被追问时被动。

## 2. 设计原理与功能框图

- **要回答的问题**：数据从哪来、经过哪些模块、以什么格式流动、输出到哪？时钟域如何划分？
- **必填字段**：总体框图（Mermaid 或图，标出 ARM/PL 边界与时钟域）、各通路的关键模块清单、数据格式（像素/样本的字宽与字节序）、控制字与寄存器地址、**数值契约**（累积是否中途饱和、四舍五入位置、饱和边界、历史状态是否跨调用保持）、控制与测量通路。
- **常见漏项**：框图只有方框没有时钟域与数据格式；只画"理想流水线"不画复位/背压；数值契约含糊（"按定点处理"），导致后面误差无法解释。

## 3. 软硬件划分依据与接口设计

- **要回答的问题**：每个功能为什么放 PS 或 PL？接口靠什么协商？两边同时访问同一资源怎么办？
- **必填字段**：划分准则表（如数据并行度、控制复杂度、存储容量、可观测性，每条配一个具体决策）、功能分配表（功能 × ARM/PL × 备注）、接口表（AXI-Stream 信号与语义、AXI-Lite 寄存器偏移、DMA 共享与加锁策略、有界轮询的超时值）、配套性约束（bit 与 HWH 必须同源等）。
- **常见漏项**：不写共享 DMA/共享总线如何避免交错；不写超时与错误处理；不写"哪些东西刻意没放进 PL"。

## 4. 验证方法与数值契约

- **要回答的问题**：凭什么说结果是正确的？错误容忍是多少？哪些工况没测？
- **必填字段**：**输入格式与边界策略**、**舍入/饱和位置**、**误差判定标准**（如"逐像素/逐样本最大误差 = 0"）、向量用例表（用例 × 模式 × 结果）、参考实现的唯一性（实现标签，如同一份参考实现供图片/视频/测量共用）、仿真与上板结果（PASS 计数）、**每条性能指标的计时口径字符串**、逐像素/逐样本误差、跨机不一致的允许范围声明、**未覆盖工况清单**。
- **常见漏项**：只给"平均误差很小"而不给最大值；两套参考实现混用导致比值不可比；口径只写"耗时"不写从哪到哪、含不含 DMA/解码/显示；把"提交的样本数"当成"已播放样本数"。

## 5. 优化过程与对比表

- **要回答的问题**：从初版到最终版改了什么？每次改动带来多少资源/时序/性能变化？哪次是转折点？
- **必填字段**：阶段表（阶段 × 功能 × 资源 × 时序）、性能对比表（见下方模板，**含口径列**）、每轮优化的动作与相对收益、**瓶颈分析**（哪个资源/哪一段耗时成为主约束）、**保留的不利证据**（对己方不利的数字）、放弃的优化方向与原因。
- **常见漏项**：只给"优化后"，不给优化前；删掉 FPGA 比 ARM 慢的条目；不写瓶颈与资源余量；用不同口径的前后数据算比值。

## 6. 大模型协作记录

- **要回答的问题**：模型在哪些环节真的有用？它给过哪些**被实测推翻**的判断？怎么发现的？
- **必填字段**：任务分解与提示词模式（可复用的模板）、被实测推翻的判断清单（判断 → 现象 → 根因 → 修正证据）、自我纠错轨迹、智能体工作流设计（生成 → 真实运行 → 用结果反驳/修正 → 写回文档）、"有效/无效"的复盘结论。**每一条都要落到可复核的文件或数据上，不把逐字对话稿当技术证据。**
- **常见漏项**：只写"用了大模型"；把模型的错误结论悄悄删掉（恰恰是最有价值的部分）；把协作写成产品宣传。

## 7. 技能包提炼过程

- **要回答的问题**：从哪些真实失败/观察里总结出可复用经验？怎么证明这些经验有效？边界在哪？
- **必填字段**：经验来源分类（上板失败 / 数值不一致 / 口径与结论争议）、每条经验对应的**可重跑检查**、失效条件的写法、通用技能与题目解耦的方式（不引用本队业务名词的部分是哪些）。
- **常见漏项**：收录"可能会踩的坑"而非真实发生的问题；只写结论不配检查；不写失效条件，导致别人照搬后失效。

## 8. 复现说明

- **要回答的问题**：一个陌生人拿着仓库和一块板，能否从零跑出同类结论？
- **必填字段**：环境准备（器件文件、工具版本、Python 依赖、板卡镜像、**磁盘空间**、素材授权要求）、逐步命令、**每步的通过判据**（文件存在 / 报告含通过字样 / PASS 计数）、结束与恢复流程（如何停止、如何恢复原 Overlay）、常见失败与处置入口。
- **常见漏项**：只给"一键脚本"不给判据；不写素材必须自备且需授权；不写如何退出，导致别人把板子留在异常状态。

## 9. 边界与未验证项

- **要回答的问题**：哪些结论**没有**被验证？什么情况下这些结论不成立？
- **必填字段**：**未验证项清单**（逐条编号，写清"为什么没验证"与"怎么才算验证"）、不宣称清单（不做整体加速比、不宣称零时延、不宣称物理接收已验证）、资源余量警告、工具/系统版本不受官方支持的情况、根因未定位的历史故障、安全与使用范围（无认证的接口不要暴露到公网）。
- **常见漏项**：用"应该可以"替代证据；把 PHY 层状态（如输出使能寄存器）当作功能已验证；漏掉"工具版本不在官方支持列表"这类合规边界。

## 10. 结论与后续工作

- **要回答的问题**：做完之后实际达到了什么（有证据）？下一步按什么优先级做？
- **必填字段**：结论段（每条结论后括注证据文件）、后续工作按约束紧迫度排序（每条写清"为什么是它优先"）。
- **常见漏项**：结论里重复摘要表格；后续工作写成愿望清单（"进一步优化性能"）而没有约束依据。

## 写作纪律（5 条）

1. **不删对己方不利的成本与数字。** 平滑/直通类效果硬件更慢就写更慢；DRC 有告警就写"6 项非致命告警"，不写成"无告警构建"。
2. **不同口径不给比值。** 单算子调用口径与整链路播放口径分别报告；"单算子 2.79×"绝不能推导成"播放快 2.79×"。
3. **未上板不写"已验证"。** 只跑过仿真就写"仿真通过（N/N）"；只看到输出使能寄存器就写"板端报告输出有效"，不写"显示器已确认"。
4. **每个数字可追溯。** 表格每行都带数据来源文件；报告里出现的统计量必须能在 `metrics/logs/` 或 `metrics/logs/` 中找到对应字段，不允许手改数字。
5. **结论每条带证据、边界与不适用的场景一起写。** 包括工具版本不受官方支持、资源余量不足、参数不可在线调整、接口无认证等；写清"什么情况下本结论不成立"，比多写一段表扬更可信。
