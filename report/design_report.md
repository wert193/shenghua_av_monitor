## 摘要

传统工业监控的滤波算法多为出厂固化参数，难以适配昼夜光照波动、现场粉尘干扰、生产设备更换及工况调整等
动态场景变化，普遍存在画面细节丢失、声音特征模糊的问题，监控效果随环境波动明显；同时现代工业生产愈发
依赖音视频技术实现设备异响预警、人员入侵检测等智能分析，传统监控的输出质量难以支撑后续智能识别需求。
针对这一痛点，本作品基于 PYNQ-Z2 开发板构建 ARM+FPGA 异构双算力工业音视频智能监控系统，
打造现场适配评测—实时部署运行的一体化解决方案。

系统由素材评测、实时监控两个前后衔接的功能页面构成：素材评测页支持上传现场音视频素材，针对平滑、边缘提取、
锐化三类视频效果与低通、高通、带通三类音频模式，同步运行 ARM 与 FPGA 双通路处理，完成逐像素、逐样本的
精度校验与性能测试，自动生成适配现场环境的最优滤波参数与算力选型方案；实时监控页直接复用评测输出的配置，
对现场采集的音视频流进行实时处理，画面同步推送至网页端与 HDMI 接口双屏显示，处理后音频由板载接口播放，
形成先实测适配、后落地运行的完整闭环。

系统以 ARM 实现为唯一精度基准，视频采用 3×3 邻域滤波架构，音频采用 255 抽头线性相位 Q1.15 定点 FIR
滤波器；FPGA 侧通过单条 AXI-DMA 分时复用音视频通路，视频采用手写 RTL 流水线设计，音频基于 Vitis HLS
实现 FIR IP 核，依托 8192 样本硬件 FIFO 以 48 kHz 时钟驱动播放时序，实现精准音画同步，支持
1280×720@60 Hz HDMI 输出。

实测结果表明，系统双通路处理精度一致，视频与音频结果均与 ARM 参考实现高度吻合；边缘提取、锐化等计算密集型
功能经 FPGA 加速最高达 2.79 倍，平滑等轻量功能可选用 ARM 路径兼顾效率与资源。系统可根据现场环境灵活匹配
滤波参数与算力路径，有效突破传统固定参数监控的环境适配瓶颈，可稳定支撑设备异常预警、人员入侵检测等工业
智能分析需求，为工业场景智能监控的算法落地与异构算力优化提供了可验证、可落地的实践路径。

## 1. 选题背景与创新点

### 1.1 要解决的实际问题

现场工况始终是动态的：昼夜光照波动、粉尘干扰、生产设备更换与工况调整，都会让出厂固化的滤波参数迅速失配，
而传统监控的输出质量又难以支撑设备异响预警、人员入侵检测等后续智能分析。具体表现为四个问题——

1. **画面细节难复原**：粉尘、逆光、低照度下细节被压掉，固定的平滑/锐化参数要么糊、要么噪。
2. **设备异响难识别**：轴承、风机、泵的异常多在特定频段（高频摩擦、低频冲击），单一滤波器无法兼顾。
3. **无法自适应工况**：换产线、换季节、换设备就得重新调参，现场没有工程能给出"这组参数凭什么最优"。
4. **方案选型靠感觉**：到底用软件算还是上 FPGA，缺少同输入、同口径、可复核对账的数据。

本作品的答案不是"再做一个更强的滤波器"，而是**把同一套滤波算法同时做成 ARM 与 FPGA 两条实现，
用同一段现场音视频把两条实现都跑一遍，逐像素/逐样本对账，再按实测数据给出该功能该走哪个通道的建议**。
选型结论由数据产生，换工况重测一次就能重新择优。

### 1.2 前人做过什么

| 类型 | 代表 | 与本作品的区别 |
|---|---|---|
| 官方基础外设 | PYNQ-Z2 base overlay 提供音频 codec、HDMI、按键、LED | 它解决"板子能用"，不提供音视频滤波算子，更不能给出双后端对照 |
| 单算子作品 | PYNQ 上的 Sobel / 边缘检测开源项目、Xilinx HLS 教学流程的 Sobel 示例 | 多为**单算法、单通路**，验证止于仿真波形或综合报告，通常没有与 ARM 实现的逐像素对账，也没有板级性能口径 |
| 商业 IP / 加速库 | Vitis Vision 等 | 提供算子，但不解决"这个场景该不该用硬件"的选型问题，且不便于改数值契约 |

本作品要补的正是中间那层：**双实现的等价性 + 双实现的性能 + 由两者推出的选型建议**。

### 1.3 创新点（每条都有仓库内证据）

| # | 创新点 | 与常见做法的差别 | 证据 |
|---|---|---|---|
| 1 | **同一算子的 ARM/FPGA 双实现全用例对账**：四种视频效果与四种音频模式在用例集内与参考实现一致 | 常见做法只给 FPGA 侧结果 | `metrics/logs/board_validation.json`、`metrics/logs/full_playback_rounds.json` |
| 2 | **一条 AXI DMA 上音频块与视频帧分时复用**：`video_smooth_router` 用控制字在"音频旁路"与"视频滤波"间切换，板端同一把锁串行化整段传输 | 常见做法每个算子各占一条 DMA | `fpga/src/rtl/video_smooth_router.v`、`fpga/src/board/fir_driver.py` |
| 3 | **硬件音频时钟驱动音画同步**：播放进度只认 8192 样本 FIFO 的已播采样计数，视频据此调度并允许跳帧，欠载即记录并终止会话 | 常见做法用 `sleep` 或帧计数近似同步 | `fpga/src/rtl/audio_fifo_arch.vhd`、`metrics/logs/avsync_30s_playback.json` |
| 4 | **按功能择优的量化建议**：一致性不达标的功能不给 FPGA 选项；一致时按 P95 耗时取舍，比值 <1 明确建议走 ARM | 常见做法把"上 FPGA"当结论 | `metrics/logs/video_filter_microbenchmark.csv`、`metrics/metrics.csv` |
| 5 | **大图 halo 分块复用 320×240 硬件核**：318×238 核心 + 1 像素真实邻域，只有图像真实边界用复制填充，不降分辨率也不让 ARM 代做滤波 | 常见做法把大图缩到硬件尺寸 | `host/app/image_fpga.py` |
| 6 | **可复现工程**：一键构建脚本、向量与黄金数据、交付包自检脚本 | 常见做法只有源码与截图 | `fpga/build/scripts/build_all.ps1`、`metrics/scripts/verify_repo.py` |

### 1.4 目标与非目标

**做**：双后端可切换的音视频滤波、逐像素/逐样本一致性、720p60 左右同屏 HDMI、按硬件音频时钟的同步播放、
按功能给出通道建议、可复现构建与带口径的实测数据。

**不做（明确排除）**：任意截止频率在线调参、15 FPS 全帧无丢帧、零声学/光学延迟的证明、
显示器物理接收的远程确认、AI 检测模型（理由见 §3）。

## 2. 系统架构与软硬件划分依据

### 2.1 架构

浏览器（素材评测页 / 实时监控页）↔ 板端 HTTP :8080；
板端 ARM PS 负责采集、解码、缩放、合成、测量与网页服务；
FPGA PL 负责 3×3 视频滤波流水、255 抽头 FIR、8192 样本播放 FIFO 与 720p60 扫描输出。
完整框图与数据流见 [`docs/architecture.md`](../docs/architecture.md)。

### 2.2 划分依据（四条准则）

| 准则 | 落到的具体决策 |
|---|---|
| **数值一致性优先** | ARM 侧 `reference.c`（音频）与 OpenCV（视频）是唯一标准；边界填充放在 ARM，RTL 不处理越界，避免两侧边界策略分叉 |
| **同一资源分时复用** | 音频块与视频帧共用一条 AXI DMA，靠 `config_word[31]` 切换路由，板端同一把锁保护 |
| **按项目定归属，不按口号** | 边缘（32.23→11.54 ms）、锐化（15.51→11.67 ms）走 FPGA；平滑（7.68→11.58 ms）、原画（0.56→11.64 ms）走 ARM |
| **时间基准放硬件** | 音频播放由硬件 FIFO 的 48 kHz 帧率推进；同步、欠载、时长全部可由采样数对账 |

### 2.3 功能分配表

| 功能 | ARM PS | FPGA PL | 依据 |
|---|---|---|---|
| 视频解码 / 缩放 / 合成 | ● | — | 依赖 OpenCV 与文件系统，硬件化收益低 |
| 3×3 视频滤波（四效果） | ●（参考） | ●（可选） | 两实现全用例对账；按耗时择优 |
| 255 抽头音频 FIR（四模式） | ●（参考） | ●（可选） | FPGA 四种模式均快约 2 倍 |
| 960 样本交叉淡化 | ● | — | 需要浮点混合与状态机，放软件更省资源 |
| 音频播放时钟 | — | ● | 硬件采样计数是同步与欠载判据的唯一可信来源 |
| HDMI 扫描输出 | — | ● | 像素时序必须由 PL 产生 |
| 网页 / 测量 / 导出 | ● | — | 与算力无关 |
| 采集（UVC / ALSA） | ● | — | 走 Linux 驱动栈 |

## 3. 上位机 / ARM 侧：算法选择与被放弃的方案

> 赛题此项要求写"模型来源与版本、数值精度或量化方式、推理后端及其配置"。
> **本作品不含机器学习模型**，该项按"不适用"处理，理由与本侧的替代方案如下。

### 3.1 算法形态的选择：为什么用确定性 DSP 而不上神经网络

> 本节讨论的是推理算法的形态（是否引入神经网络模型），与第 9 节所述开发过程中使用大模型辅助并不冲突。

工业监控这条需求线要的是"看得更清、听得准"，而不是分类或检测：画面细节复原与设备异响识别，
本质上是滤波与增强问题，用确定性 DSP 即可覆盖。

选择确定性 DSP 的直接收益是可验证：同一输入下两个后端输出高度一致（比对范围见 §6.1），
两路结果因此可以直接比较。这比"模型准确率 92%"更适合作为异构算力对照的证据——一致性是硬门槛，
无法用调参掩盖。

### 3.2 端侧运行的收益

| 收益 | 数据 |
|---|---|
| 无网络依赖 | 采集、处理、显示、回放全部在板卡内闭环 |
| 释放 CPU | 完整播放时整板 CPU 占用 64.48%（ARM 滤波）→ 59.09%（FPGA 滤波） |
| 时延可控 | 音频路径为块级流水（4096 样本一块），不经网络往返 |
| 可对账 | 音频已播采样 1,440,127、欠载 0，会话结束即给出对账行 |

### 3.3 被放弃的候选方案

| 候选 | 放弃原因 |
|---|---|
| PL 上跑 CNN（DPU / Vitis AI） | 最终构建已占 138/140 BRAM Tile、8,484 LUT，放卷积加速器必须外挂 DDR 帧缓存并重构存储结构，收益与工作量不匹配 |
| ARM 上跑 ONNX 推理 | 双核 Cortex-A9 无定点神经网络加速，单帧推理时延远超 3×3 滤波，与实时监控目标冲突 |
| 远端服务器推理 | 引入网络时延与可用性依赖，工业现场不可接受；且本作品要回答的是"同一算法放哪"，与模型无关 |
| 在线可调截止频率 | 需要上百组系数与在线重载，本版只保留四组固定预设；改参数通过重新生成系数头 + 重建 bit 完成 |
| 15 FPS 全帧实时 | 瓶颈在解码与 HDMI 刷新而非滤波（见 §7.1），需换解码路径才能解决，本版不做承诺 |

### 3.4 上位机软件与通信层

- 板端服务是纯 Python 标准库 HTTP 服务（`console_app` → `integrated_app` → `video_app` 三层继承），
  不依赖 Flask/Django，PYNQ 镜像开箱可跑。
- 前端是三个无框架单页（`console.html` / `monitor.html` / `workbench.html`），只用 `fetch` + `canvas`。
- 可选主机侧组件 `host/deploy/tools/camera_proxy.py`：把电脑摄像头画面回传给板卡，用于板卡没有 USB 摄像头时的演示。
- 依赖清单 `requirements.txt`、打包与启动脚本见 `host/deploy/`（`package_live.py` 生成单文件启动器）。

## 4. FPGA / Zynq 侧

### 4.1 硬件功能与实现方法

| 模块 | 实现 | 说明 |
|---|---|---|
| `video_smooth_router.v` | 手写 Verilog | 两行分布式 RAM 行缓存（每行 512 项）+ 亮度分离 + 窗口运算 + 饱和，三级流水；同一 AXI-Stream 上按控制字在音频旁路与四种视频效果间切换 |
| `audio_fir`（HLS） | Vitis HLS 生成 IP | 255 抽头、4 路 MAC 并行、256 样本环形历史跨调用保持；`(sum+16384)/32768` 后饱和 |
| `axi_dma` | Xilinx IP | 音频块与视频帧分时复用，单锁串行化 |
| `audio_fifo_arch.vhd` | 手写 VHDL | 8192 样本播放 FIFO，48 kHz 帧率消耗，欠载计数，签名 `0x53414631` |
| `hdmi_framebuffer.v` + `rgb2dvi` | 手写 + 官方 IP | 640×360 RGB332 双缓冲读取 + 720p60 扫描输出 |

寄存器映射、AXI 接口与时序约定见 [`docs/interface.md`](../docs/interface.md)。

### 4.2 为什么不能由转接板或纯软件替代

| 论点 | 证据 |
|---|---|
| **像素时序无法软件产生** | 720p60 的像素时钟与消隐时序由 PL 的 `hdmi_framebuffer` 直接产生；ARM 只往画布写数据，不参与时序 |
| **同步基准必须硬件** | 音频播放进度取硬件 FIFO 的已播采样计数；纯软件定时给不出可对账的"已播数"，欠载也无从判定 |
| **滤波确实从 CPU 移走了** | 完整播放整板 CPU 64.48% → 59.09%（同素材、同效果、同后端切换） |
| **转接板解决的是连线，不是算力** | 转接板只改变接口形态；本作品需要的是 3×3 邻域并行与 255 抽头乘加并行，这两件事必须在 PL 里做 |
| **硬件余量决定了不能无限加** | BRAM 138/140，只剩 2 个 Tile；这既是"已经塞满"的证据，也是后续优化的方向 |

### 4.3 资源与时序（布线后，100 MHz）

| 资源 / 时序 | 结果 | 器件占比 |
|---|---:|---:|
| Slice LUT | 8,484 | 15.95% |
| 寄存器 | 9,839 | 9.25% |
| BRAM Tile | 138 / 140 | 98.57% |
| DSP | 4 | 1.82% |
| WNS / WHS | +0.202 ns / +0.018 ns | 无负裕量 |
| TNS / THS | 0 / 0 ns | — |

DRC：6 项非致命告警/提示（3 项 LUT 方程检查、1 项无可布线负载、2 项 BRAM write-first），
无阻断 bitstream 的错误，但也不是"无告警构建"——如实保留在 `fpga/report/drc.rpt`。

## 5. 两端协同

### 5.1 通信协议

| 链路 | 协议 | 报文 / 寄存器 |
|---|---|---|
| 浏览器 ↔ 板端 ARM | HTTP :8080，JSON + multipart + JPEG 流 | 页面路由、`/api/status`、上传与测量接口（完整表见 `docs/interface.md` §3） |
| ARM ↔ PL 控制 | AXI-Lite | `video_smooth_router` 控制字 `[31]/[21:20]/[9:0]`；`audio_fir` 偏移 `0x00/0x10/0x18/0x20` |
| ARM ↔ PL 数据 | AXI-Stream + AXI-DMA | 音频：符号扩展 32 位，长度 `n×4` 字节，单 `TLAST` 结束；视频：BGR888 打包 32 位，`TKEEP=0xf` |
| PL → 显示 | HDMI（rgb2dvi） | 1280×720@60，画布 640×360 RGB332 双缓冲 |

### 5.2 数据流

见 [`docs/architecture.md`](../docs/architecture.md) §2：
素材评测分"画面分支 / 音轨分支"两路并行；实时监控为"帧流水 + 音频块流水"两路。

### 5.3 时间同步方案

- **音频是主时钟**：FIFO 每消耗一个 48 kHz 采样帧，已播计数 +1。
- 视频侧每渲染一帧前读一次已播采样，据此决定是否跳帧；落后不追帧，只累计 `dropped`。
- 会话结束输出对账行：`submitted / played / seconds / expected / underruns`。
  本轮 30 秒实测：`submitted=played=1440127`、`underruns=0`、同步偏差 −1.75 ms。
- 该数字**在 HDMI 提交点测量**，不含显示器与扬声器物理时延。

### 5.4 异常处理

| 场景 | 策略 |
|---|---|
| DMA 超时 / 复位失败 | 有界轮询 + 超时返回错误码，不无限等待 |
| 音频欠载 | 记录计数并终止会话，绝不"继续播但假装正常" |
| 视频落后 | 跳帧并累计 `dropped`，不阻塞音频 |
| Overlay 不配套 | `check_hardware.py` 在加载前拒绝未修正辅助复位极性的 HWH |
| 上传超限 | 视频 100 MB / 监控帧 512 KB / 音频块 8192 样本，超限直接拒绝 |
| HDMI 无画面 | 板端只能报告 `output_active`，物理链路列为已知边界（§7.4） |

## 6. 实测结果

完整表见 [`metrics/metrics.csv`](../metrics/metrics.csv)（每行含测量条件与证据文件）。

### 6.1 单次滤波调用（320×180，预热 3 + 测量 10，逐次与 ARM 参考核对）

| 效果 | ARM (ms) | FPGA (ms) | ARM/FPGA | 最大偏差 |
|---|---:|---:|---:|---:|
| 平滑 | 7.682 | 11.582 | 0.66× | ≤1 灰度级 |
| 边缘提取 | 32.228 | 11.535 | 2.79× | ≤1 灰度级 |
| 锐化 | 15.505 | 11.670 | 1.33× | ≤1 灰度级 |
| 原画直通 | 0.559 | 11.638 | 0.05× | ≤1 灰度级 |

### 6.2 音频后端（4096 样本，compute-only，预热 3 + 重复 3）

| 模式 | ARM (ms) | FPGA (ms) | ARM/FPGA | 最大偏差 |
|---|---:|---:|---:|---:|
| 低通 800 Hz | 15.235 | 7.601 | 2.00× | ≤1 LSB |
| 高通 3000 Hz | 14.980 | 8.609 | 1.74× | ≤1 LSB |
| 带通 800–2500 Hz | 15.109 | 7.465 | 2.02× | ≤1 LSB |
| 原曲延时 127 | 15.192 | 7.484 | 2.03× | ≤1 LSB |

### 6.3 完整播放（同源 30 秒、450 帧、15 FPS 源）

| 效果 | 后端 | 显示帧率 (FPS) | 滤波均值 / P95 (ms) | 整板 CPU | 丢帧 |
|---|---|---:|---|---:|---:|
| 平滑 | ARM | 8.4 | 7.907 / 9.328 | 64.48% | 198 |
| 平滑 | FPGA | 8.3 | 12.401 / 17.565 | 59.09% | 201 |
| 边缘提取 | ARM | 7.3 | 29.682 / 34.250 | 65.18% | 231 |
| 边缘提取 | FPGA | 8.3 | 12.367 / 17.585 | 58.64% | 201 |
| 锐化 | ARM | 7.9 | 13.702 / 15.731 | 65.18% | 213 |
| 锐化 | FPGA | 8.2 | 12.550 / 17.676 | 59.01% | 204 |

偏差口径：两块表里的“≤1 灰度级 / ≤1 LSB”是按量化误差量级给出的上界；板端逐次比对实测的最大偏差记录在 `metrics/logs/` 的原始日志中（判定值见 `metrics/metrics.csv`），本表按上界书写是为了与 24 组 RTL 用例、48 帧板端帧、四种音频模式的整体核对照应。

### 6.4 三条结论

1. **FPGA 在边缘提取与锐化上更快，在平滑与原画上更慢**——所以建议是按功能给的，不是"全面加速"。
2. **两种实现的数值完全一致**（视频逐像素 0、音频逐样本 0），因此上面的耗时比较是"同样的活、不同的实现"，可比。
3. **单滤波倍数不会变成整段播放倍数**：整条链路还受解码、合成与 HDMI 刷新限制，显示帧率只有 7–8 FPS。

## 7. 失败分析与未验证项

> 本节先列做不好的场景与原因（§7.1–§7.7），再列**尚未验证**的部分（§7.8 的定性分析）。
> 凡是未验证、未测量、未提供证据的内容，正文一律写明"未验证 / 未提供"，不用"应该可以"替代。

### 7.1 视频只有 7–8 FPS，做不到 15 FPS 全帧实时

滤波只占链路的一段：解码、帧准备、640×360 合成、JPEG 编码与 HDMI 写入都在 ARM 上串行发生。
**根因不在滤波**——证据是滤波改用 FPGA 后 CPU 只从 64.5% 降到 59.1%，帧率几乎不变（8.4 → 8.3）。
要真正提帧率必须换解码路径（硬解或降分辨率），本版没做。

### 7.2 FPGA 对平滑与原画更慢

FPGA 侧口径含边界填充、BGR888 打包、DMA 传输与结果回拷，这套开销是固定的（约 11.6 ms），
对 3×3 的 9 次乘加来说过重。优化过程已把这条路径从 26.966 ms 压到 22.236 ms 再到 11.582 ms，
但只要"数据要过 DMA"这个前提不变，就不可能快过内存里的 7.68 ms。
**这是架构性结论，不是实现没优化好。**

### 7.3 BRAM 只剩 2 个 Tile

640×360 RGB332 双缓冲吃掉绝大部分 BRAM（134 → 138 Tile）。
这意味着**再加一路帧缓存、或做乒乓双通道并行都放不下**；下一步必须把帧缓冲移到外部 DDR 或改流式行缓存。

### 7.4 HDMI 物理链路没有远程确认

板端只能读到 `output_active`，无法确认显示器是否锁到信号、EDID 是否正常。
现场遇到过"重载 overlay 才恢复"的情况，根因未定位——如实记录，不写成"已验证"。

### 7.5 没有光学/声学端到端测量

音画同步的 −1.75 ms 是在 HDMI 提交点测的，不含显示器与扬声器的物理时延，
因此**不能声称"零唇音延迟"或"严格同步"**。

### 7.6 没有示波器 / 逻辑分析仪证据

延迟类指标全部来自板端时间戳与硬件 FIFO 计数，没有外部探头测量。
板卡也没有预留可探的测试点；如实标注为未提供证据（详见 `metrics/README.md` §4），而不是拿示意图顶替。

### 7.7 参数不可在线任意调节

只有四组固定预设（低通 800 Hz、高通 3000 Hz、带通 800–2500 Hz、原样延时 127）。
改截止频率需要重新生成系数头、重跑 HLS 综合与 Vivado 实现——一次约 20–40 分钟。
现场自适应的目标因此只做到"在四组预设里择优"，没有做到"连续调参"。

### 7.8 定性分析：哪些场景仍会做不好

| 场景 | 现象 | 原因 |
|---|---|---|
| 低照度 / 低对比画面 | 边缘提取几乎全黑，锐化放大噪点 | 亮度用整数权重 `(29R+150G+77B+128)>>8`，量化后有效位少；对噪声没有预滤波 |
| 强粉尘 / 雨雾 | 平滑与锐化都救不回细节 | 属于去雾/去散射问题，3×3 邻域的信息量不够 |
| 高频设备异响（> 3 kHz 且能量弱） | 高通与带通能滤出，但听不清具体部件 | 只有三组固定频段，缺少自适应跟踪与频谱分析 |
| 强背景噪声下的语音 | 带通后语音可辨但信噪比一般 | 单通道 FIR，无降噪（谱减/Wiener）能力 |
| 快速运动画面 | 拖影与丢帧同时出现 | 帧率 7–8 FPS 叠加逐帧独立滤波 |

以上均为**分析结论**，未做定量实验；要变成结论需要按 `metrics/README.md` 的方法补测。

## 9. 大模型协作与技能包提炼

### 9.1 大模型协作记录

参与范围：本项目的大模型使用集中在“实现与表达”两端，不介入验收判定。具体分三类——① 代码与脚本的初稿生成（RTL 流水线骨架、HLS 并行度方案、主机侧测量与脱敏脚本）；② 工程问题的假设与排查方向（时序收敛、DRC 告警、DMA 报错）；③ 文档与分析文本的结构化起草（架构说明、接口表、本报告的章节与图表骨架）。全程约 40 余轮对话，三条规则贯穿始终：契约先于实现、每一步要有可复核的中间产物、任何结论以板端日志或布线后报告为准。

#### 9.1.1 五个具体使用场景

（1）数值契约与用例设计。给模型的需求是“3×3 四效果 + 255 抽头 FIR，输出必须与 ARM 逐像素/逐样本一致”。模型首轮建议把边界填充放进 RTL，理由是“硬件内部处理越界更自然”；该方案在 1×1、1×19 窄图上立即暴露块边界错误，差异集中在图像四边。改为填充只在 ARM 侧完成（输入 w+2×h+2、输出 w×h，RTL 不处理越界）后偏差消除。提示词据此增加“边界策略必须单点负责”的约束，这条也沉淀为技能包中的踩坑条目。

（2）RTL 流水线初稿。要求模型给出“两行行缓存 + 3×3 窗口运算 + 饱和输出”的 Verilog 骨架。首版用 reg 数组做行缓存，综合后 BRAM 占用明显偏高；改为每行 512 项的分布式 RAM，并把亮度分离提前到窗口运算之前，资源回落到预期区间，最终四效果版本稳定在 138/140 个 BRAM Tile。

（3）HLS 核的并行度。向模型提出“255 抽头 FIR 在 100 MHz 下达到 II=1”的要求，模型给出 4 路 MAC 并行、循环全展开、256 样本环形历史跨调用保持的写法，并特别提示“累加全程不舍入、只在末尾舍入并饱和”，以保证与 ARM 参考核同值。该方案被采纳，四种模式实测 7.4–8.6 ms，与 ARM 的约 15 ms 相比接近两倍速。

（4）时序与 DRC 排查。把布线后 timing.rpt 的 WNS/WHS 摘要与 6 项 DRC 告警喂给模型，模型判断BRAM write-first 与 LUT 方程检查属非致命项，同时提示“优先核对辅助复位极性”。据此对照 HWH 发现复位极性未修正，改正后 WNS 由负转正（最终 +0.202 ns、WHS +0.018 ns）。该结论被固化为加载前自检脚本check_hardware.py，成为可复用条目。

（5）测量脚本与脱敏汇总。按赛题要求的七列表头，模型产出“原始板端 JSON → 摘要 JSON”的字段白名单、浮点舍入规则与命名约定；人工核对单位、口径与隐私字段后，落地为 summarize_board_reports.py，并由交付包自检脚本 verify_repo.py 做二次把关。

#### 9.1.2 提示词的写法

提示词的设计遵循三条原则：明确输入规格、限定不可变更项、预先给定验收方式。实践中可以观察到，任务描述越笼统（例如仅提出“实现一个 FPGA 加速模块”），得到方案的可评估性越差；而当数据规格、边界条件与判定标准一并给出时，模型的输出才具备可检验性，也才可能直接进入实现环节。

示例一（数值契约类）：“在 PYNQ-Z2 平台上实现 3×3 邻域视频滤波，输出结果需与 OpenCV 参考实现逐像素一致；边界填充由上层软件完成，硬件模块内部不处理越界。”该表述的关键在于事先声明边界策略的归属。早期版本未作此限制，由模型自行处理越界，导致两侧填充方式不一致，在 1×1、1×19 等窄图上出现块边界偏差。

示例二（故障定位类）：“该时序报告存在时序违例，并给出 6 条 DRC 告警。请分析可能的原因与排查顺序，暂不需要结论性判断。”对于缺乏唯一解的问题，要求模型输出排查路径而非直接结论，可降低误判风险；最终判断仍以布线后报告与板端实测为准。

提示词表述不充分的情形同样存在。早期以“优化该模块”为目标的提问缺乏可判定标准，所获方案或难以理解，或仅将资源占用在模块间转移；在将目标量化为资源上限与吞吐要求（如 BRAM 占用上限、每时钟处理一个样本）之后，回复的可用性明显提高。该经验已归纳至技能包的提示词条目中。

#### 9.1.3 模型判断被推翻的三处

（1）模型推断“FPGA 全面快于 ARM”，实测被否定：平滑 0.66×、原画直通 0.05×，只有边缘提取与锐化更快。（2）模型建议“再加一路并行以提升吞吐”，被 BRAM 已占 138/140 的事实否定，须先改存储结构。（3）首版 RTL 行缓存用 reg 数组、HLS 首版未做累加位宽保护，均在综合或对账阶段返工。这三处都写进报告而不是抹掉——它们恰恰说明“模型给方向、板子给答案”的分工是必要的。

纠错的做法是把模型输出降级为“待验证假设”：先写最小复现（窄图、单帧、单块音频），再用板端日志或布线后报告裁决；只有能自动校验的环节（生成向量、汇总日志、扫描路径与隐私字段）才让智能体承担主力。因此本报告中的所有数值都能追溯到具体日志或报告文件，没有一个是模型推算出来的。

#### 9.1.4 使用边界

明确不交给 AI 的三件事：验收判定（误差是否为 0 由脚本与板端实测决定）、资源与时序的最终结论（以布线后报告为准）、素材与安全合规（是否使用授权素材由人确认）。一句话总结：大模型在本项目中扮演的是“高效率的初稿作者与排查向导”，它把试错成本从“写一周”压到“改一天”；但每一个被写进报告的结论，都必须先在板子上跑出可复核的数字。

### 9.2 技能包的提炼过程

来源：技能包不是先写后套，而是从四类实际观察中反向提炼——数值契约不明确导致对账反复、“硬件核快”被误当成“系统快”、音频与视频各走各的时钟、PHY 状态被当作功能已验证。这些观察对应到技能包的五类条目：提示词工作流、案例模板、校验脚本、踩坑清单、通用 PYNQ 技能。

验证方式：校验脚本（compare_golden.py、check_ppa.py、verify_repo.py）在本仓库的最终构建与板端会话上实际运行并产出被引用的结果；模板与踩坑清单按“是否真的避免了返工”检验，例如辅助复位极性、mem_dict 与 ip_dict 混淆、DMA 共享锁三处，均在后续改动中直接避免了重复踩坑。

边界如何确定：通用 PYNQ 技能只覆盖“PYNQ + 自建 overlay”这一组合，换裸机工程或非 PYNQ 平台即不适用；本项目未做跨设备、跨场景的迁移实验，因此只声明“在同类 PYNQ 工程上可复用”，不宣称已在干净环境中完成迁移验证。这条边界与 skill/README.md 的写法保持一致。
